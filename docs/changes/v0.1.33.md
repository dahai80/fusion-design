# v0.1.33

## Summary

Issue #52 closure: nightly-20261128 design regression (d28/d29/d30, 90.0% vs 100.0% floor) traced to one shared root cause — the eval-time server ran without `FUSION_CLIENT_KEY`, so every `/api/generate` returned `fusion-mlx HTTP 403` and no session could be created. `start.sh` now resolves the key durably instead of only warning.

## Changes

- **start.sh client-key resolution** (PR #53): same chain as fusion-supervisor `env_map.rs read_gateway_client_key()` — `FUSION_CLIENT_KEY` env first, then gateway config `auth.api_keys` (the `name=admin` all-model wildcard entry wins, else the first entry with a key; `FUSION_GATEWAY_CONFIG` overrides the path). The resolved key is exported to the server process and never logged or echoed; the loud warning remains for when both sources fail.
- The awk state machine handles both YAML field orders observed in the wild (key-before-name and dash-prefixed `- key:` fields).

## Verification

- Resolver unit-checked against the real gateway config (48-char key, length-checked only) and two fixtures (admin-preferred; no-admin first-entry fallback).
- Live E2E: `env -u FUSION_CLIENT_KEY ./start.sh start` → server log `FUSION_CLIENT_KEY resolved from gateway config (auth.api_keys[admin])` → real-model `POST /api/generate` returns a 21-node session (previously `fusion-mlx HTTP 403`).
- PR #53 full CI green (fmt/clippy/test/wasm, check+test macos, deny×3, cargo-audit).
