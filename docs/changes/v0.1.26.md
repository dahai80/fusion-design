# v0.1.26

## Summary

Issue #36 closure: unknown `/api/*` paths now return 404 (not a misleading 405); share-base claim refuted with evidence.

## Root cause

The acceptance run (2026-11-03, via the gateway shell) probed `/api/v1/health` and `/api/v1/designs` — paths from the fusion-artifacts-engine convention that fd-server has never exposed — and the router's `/api/*` catch-all returned **405 "无 GET 路由"** for any unknown API path. That was a router defect: 405 means "path exists, wrong method", so the report read it as "route registered with the wrong method".

Third finding ("frontend bundle references `api/v1/share-base` and `api/v1/share/{id}`") is not reproducible: `grep -rn "api/v1\|share-base\|share/"` over `crates/fd-server/` returns zero hits — the served bundle references only the module-relative `/api/*` surface documented in `docs/API.md`. Share-link state (`share_id`) lives in fusion-artifacts-engine's data model, not in this repo.

## Changes

- Router: unknown `/api/*` paths → **404** `{"error":"not found"}`; 405 reserved for known paths with a wrong method (with the GET hint for read-only endpoints). New `known_api_path` route inventory — adding a route requires updating it, `docs/API.md`, and the contract tests.
- `docs/API.md`: 404 row now covers unknown paths.
- Contract test `unknown_api_paths_are_404_not_405` pins the behavior for the exact probed paths (`/api/v1/health`, `/api/v1/designs`, `/api/v1/share-base`).

## Verification

- 546 tests green (36 suites); fmt / clippy -D warnings / deny×3 green.
- Live: `GET /api/v1/health` → 404, `GET /api/v1/designs` → 404, `POST /api/tokens` → 405 + hint, `GET /api/health` → 200.
